## 6. Key decisions & rationale
- **FAST_COMPILE = non-parity CPU only** — gated on `policy.parity_mode` + `jax_platform=="cuda"`. It reduces XLA passes → could shift CPU reduction order → withheld from bit-exact parity lanes. GPU relief comes from the persistent cache, NOT FAST_COMPILE.
- **Persistent cache = SAFE narrow mode** (`xla_gpu_per_fusion_autotune_cache_dir`), never `"all"` — the broad mode forces nvlink through the container toolkit (the cu1290 block). The main executable cache (`jax_compilation_cache_dir`) works regardless of mode.
- **`SIMSOPT_JAX_CUDA_LIBRARY_MODE=bundled`** on the pod (jax wheel's CUDA), NOT the old `=local`+manual-CUDA-12.9 approach that caused nvlink.
- **Deploy via `--templateId`** (cached nodes) not raw `--imageName` (cold pulls) — THE fix for slow boots.
- **Fair-compare launcher deliberately NOT given the cache** — it *measures* compile time; a warm cache would contaminate it.
- Seeds: the big exploration loops (`order2_topology_loop` 467, `closed_loop_3lane`, `overnight`, `keepout_loop`) are off-spec/debug/chaotic → **0 usable**. Usable seeds are the curated dirs (`april_signed_donor_probe`, `edge_envelope_vacuum/seeds`, `prod0142`, `loop_2026-05-18`, `champion_topology_lanes`). **No mpol2 seeds exist** (lowest mpol8); mpol2 mechanism check uses the repo fixture via self-compile.

## 6b. nvlink block — ROOT CAUSE & FIX (2026-06-15, CONFIRMED on pod `uejmhaf19c9kv3`)
The `nvlink fatal: input file newer than toolkit (129 vs 124)` block is a **toolkit version mismatch**, NOT a code bug:
- JAX 0.10 `jax[cuda12]` bundles **ptxas 12.9** (emits "129" cubins) in `site-packages/nvidia/cuda_nvcc/bin/ptxas` but ships **NO nvlink**. The `runpod/pytorch:...cuda12.4.1` image's only nvlink was **12.4**, which rejects 129 cubins. XLA needs nvlink to link multi-module GPU compiles (large graphs like single-stage; small graphs are single-module and never hit it — so it can't be reproduced with a toy matmul).
- **REFUTED (with proof):** XLA's own suggested bypass `XLA_FLAGS=--xla_gpu_enable_llvm_module_compilation_parallelism=false` is a **NO-OP in jaxlib 0.10** — I instrumented every python PID (sitecustomize writing `XLA_FLAGS`) and the exact PID that hit nvlink HAD the flag set, yet XLA still shelled out to nvlink and still printed the "please use this flag" hint. Adding `libnvJitLink.so.12` (12.9, present + loadable) to `LD_LIBRARY_PATH` also did NOT divert XLA off the nvlink binary.
- **FIX (works, keeps parallel compile):** `apt-get install -y cuda-nvcc-12-9` (apt-installable from the image's configured NVIDIA repo; gives `/usr/local/cuda-12.9/bin/{nvlink,ptxas}`, both build `compiler.36037853` = same as bundled ptxas) + `export XLA_FLAGS="--xla_gpu_cuda_data_dir=/usr/local/cuda-12.9"`. Now compiler+linker both 12.9 → matches the cubin → clean. (Alt that also works: `--xla_gpu_cuda_data_dir=/usr/local/cuda` forces system ptxas 12.4 → 124 cubin → system nvlink 12.4; verified jaxlib 0.10 PTX compiles under ptxas 12.4. The 12.9 route is preferred — no downgrade risk.)
- **For the committed launchers:** `prepare_cuda_gpu_lowres_tests.py:462` sets `XLA_FLAGS=CUDA_DETERMINISM_XLA_FLAG` (overwrites). To make RunPod runs nvlink-clean out of the box, that launcher's `_cuda_env` should append `--xla_gpu_cuda_data_dir=/usr/local/cuda-12.9` (and the runner should `apt-get install cuda-nvcc-12-9`). NOT yet committed — candidate follow-up.
