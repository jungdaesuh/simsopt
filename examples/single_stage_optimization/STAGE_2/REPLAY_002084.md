## Run

One shot (creates `<repo>/.venv-replay`, installs deps, runs with 4 threads; override with
`OMP_NUM_THREADS` / `REPLAY_VENV`). It needs a prebuilt `build/<abi-tag>/simsoptpp*.so` matching the
interpreter. **`build/` is gitignored, and this tree does not compile with GCC 12-15 or Apple Clang 21**
(`xt::pyarray` `operator*=` is ambiguous between the vendored xtensor 0.21 and pybind11; reproduced here
with GCC 12, 13 and 15, independent of numpy version; the repo's own `reports/SUMMARY.md` records the
same failure on Apple Clang 21). So ship `build/` alongside the repo, or apply simsopt-surrogate's
`xtensor_compat` refactor to `src/simsoptpp` before building.

Prebuilt extensions shipped under `build/` (both built from this exact `src/simsoptpp`, which has not
changed since the March baseline pin `bf46e107`):

| file | platform | built | needs |
|---|---|---|---|
| `build/cp311-cp311-macosx_arm64/simsoptpp.cpython-311-darwin.so` | macOS arm64 (Apple Silicon) | 2026-03-15, from `hbt-compare/envs/baseline-original` | CPython 3.11 arm64, numpy >= 2.4 |

**That is the only prebuilt binary in this repo, so the replay is Apple-Silicon-only in practice.**
An earlier revision of this file also listed a Linux x86_64 build
(`build/cp311-cp311-linux_x86_64/simsoptpp.cpython-311-x86_64-linux-gnu.so`, built 2026-07-13). That
file has never been committed here — `git ls-files build/` returns the macOS binary alone. A Linux
x86_64 build does exist on the `playstation` host and would have to be copied in deliberately.

The launcher finds the arm64 file automatically by matching the interpreter's SOABI tag
(`cpython-311-darwin`). An Intel Mac, a Linux box, or any non-3.11 Python has no prebuilt binary here
and falls through to the compile path, which fails as described above.

Runtime deps beyond simsopt's declared ones: `shapely` and `numba` (both imported by this driver;
neither is in `pyproject.toml`). **`jax` and `jaxlib` are pinned to 0.10.0 in the launcher and the
pin must not be relaxed** — see "What to expect" below. The equilibrium is read with
`scipy.io.netcdf_file`, so `netCDF4` is not needed.

`banana_coil_solver.py` takes no arguments — every weight, threshold and geometry constant is a
module-level literal. To stop those literals drifting away from the run being replayed, that April
run's own `results.json` is shipped here verbatim as `replay_002084_root_results.json` (sha256
`655c7f3e…`), and the driver checks 19 constants against it immediately before `minimize()`:

```
replay contract OK: 19 constants match the 2026-04-15 root run
```

On drift the run aborts naming each offending constant and both values, rather than producing a coil
that is not the root. Checked: the eight objective weights and thresholds, plus `MAJOR_RADIUS`,
`TOROIDAL_FLUX`, `banana_surf_radius`, `NFP`, `order`, `max_iterations`, the four banana seed
parameters and `PLASMA_SURF_FILENAME`.

The launcher also generates `src/simsopt/_version.py` when it is absent. `setuptools_scm` writes
that file at build time and `.gitignore` excludes it, so on a fresh clone the prebuilt-extension
path — which puts `<repo>/src` on `PYTHONPATH` without installing simsopt — would otherwise fail
with `ModuleNotFoundError: No module named 'simsopt._version'` at `src/simsopt/__init__.py`.
The equilibrium `../equilibria/wout_nfp5ginsburg_000_002084_iota20.nc` (sha256 `05d5eb6f…`) matches
`wout*.nc` in `examples/.gitignore` but is force-tracked on this branch since `3c59034e`, so a clone has it.

## What to expect

Original endpoint: 300/300 iterations (cap), length 1.844 m, max curvature 60.75 /m,
coil-coil 0.04993 m, banana current 15816 A, field error 1.03e-2, volume 0.09194.

The per-evaluation objective trace matches the original `run.log` exactly for the first 15
evaluations and then drifts. The first differing evaluation is 16, and the only field that differs
is the `Curvature=` column (the raw `LpCurveCurvature` value), by 8.8e-10 relative; `J`, `Jf`,
`⟨B·n⟩`, `Len` and `‖∇J‖` stay bit-identical through evaluation 22. The C++ Biot-Savart path is
therefore not the source of the drift.

**The cold start is a line-search knife edge, and the jax version does not decide it.** The Lp(4)
curvature penalty reaches 1e13 on L-BFGS-B trial steps around evaluations 16-26. After the trial at
evaluation 21 (Curvature 2.7e13, coils touching) the April run's line search found a new point at
evaluation 24 and went on to the 300-iteration cap; a replay whose last bits differ can instead
re-evaluate the same point five times and exit on ftol at iteration 8 with a 0.5-0.6 m coil.
Measured 2026-09-16, one launcher, fresh venvs, shipped prebuilt extensions:

| platform | jax | OMP threads | iterations | length | outcome |
|---|---|---|---|---|---|
| original (2026-04-15, macOS) | unknown | 4 | 300 (cap) | 1.8443 m | reference |
| macOS arm64 (serial .so) | 0.10.0 | any | 300 (cap) | 1.8463 m | root basin |
| macOS arm64 (serial .so) | 0.10.2 | any | 49 (ftol) | 0.5025 m | stall |
| Linux x86_64 | 0.10.0 | 4 | 8 (ftol) | 0.5967 m | stall |
| Linux x86_64 | 0.10.0 | 1 | 32 (ftol) | 0.5479 m | stall |
| Linux x86_64 | 0.10.0 | 8 | 288 (ftol) | 1.8484 m | root basin |
| Linux x86_64 | 0.10.2 | 4 | 300 (cap) | 1.8461 m | root basin |
| Linux x86_64 | 0.10.2 | 1 | 300 (cap) | 1.8488 m | root basin |

Repeats of one configuration also disagree on the OpenMP build: Linux jax 0.10.0 at 8 threads went
288 iterations once and stalled at 51 the next time; at 4 threads it stalled at 8 and then at 49. Roughly
two thirds of Linux attempts stall. So the macOS finding (0.10.0 reproduces, 0.10.2 stalls) is one
sample per version and reverses on Linux. What flips the outcome is any last-bit perturbation: the jaxlib build on a serial macOS
extension, the OpenMP thread count on the Linux one. The launcher therefore checks the outcome
against `replay_002084_root_results.json` (>= 250 iterations and length within 5 % of 1.844 m
counts as the root basin; < 100 iterations and < 1.0 m is a stall) and retries a stall with a
different `OMP_NUM_THREADS`. On a serial build the retries are bit-identical and it reports instead.
The jax pin is kept for environment reproducibility only. numpy (2.4.2 vs 2.4.6) and scipy were
varied independently on macOS and change nothing.

**The 0.10.2 stall is macOS-specific, and the pin should not be described as fixing a general jax
regression.** On Linux x86_64, jax 0.10.2 runs this replay to 284, 293 and 300 iterations in the
original's basin — never 49.

**BLAS is not the variable — measured, not assumed.** The obvious hypothesis was Accelerate (what
pip numpy wheels use on macOS arm64) versus the conda-forge OpenBLAS the April environment likely
had. It is wrong. Building a conda-forge env with `libblas=*=*openblas` (`libopenblas_armv8p-r0.3.34`,
verified by `otool -L`), matched scipy 1.17.1 and numpy 2.4.6, and re-running both jax versions gives
**bit-identical traces to the Accelerate runs** — every printed evaluation, both versions:

| BLAS | jax 0.10.0 | jax 0.10.2 |
|---|---|---|
| Accelerate | 558 evaluations | 125 evaluations |
| OpenBLAS | 558 evaluations (trace bit-identical) | 125 evaluations (trace bit-identical) |

So the stall is **jax 0.10.2 on macOS arm64, independent of BLAS** — the macOS `jaxlib` build
itself, not an interaction with the linear-algebra backend.

**The 8.8e-10 residual at evaluation 16 remains unexplained, and the search is closed.** It is
identical under jax 0.9.2 / 0.10.0 / 0.10.2 and under both BLAS backends (`Curvature=11396385.79`
in all four runs, against the April log's `11396385.80`). Ruled out: the jax version, the BLAS
backend, numpy (2.4.2 vs 2.4.6), `OMP_NUM_THREADS`, the C++ and Python sources (byte-identical to
`ed120da4e230`), and the compiled extension (three independent builds give bit-identical
`kappa`/`gamma`/`gammadash`). Remaining candidates — the exact scipy minor, the compiler of the
April `.so`, libm — have **no recorded target to chase**: the April environment's package versions
were never recorded anywhere, and `ed120da4e230` pins nothing (`numpy>=1.21`, `jax>=0.2.5`,
`scipy>=1.5.4`). Further archaeology is not worth it; the replay's stated purpose is met.

### The artifact of record

`replay_002084_root_biot_savart.json` in this directory is the April run's own output, shipped
verbatim (sha256 `07f944106af618e6...`). **Use it, not a replay, wherever the geometry matters.**
A replay lands 11.7 mm rms / 23.1 mm max from it, so regenerating the coil to obtain it is a
mistake; the replay demonstrates the method and the basin, the file is the coil.

### Superseded explanations

Two earlier claims in this file were wrong and have been removed:

- *"the seed differs by 3 ulp (`…919` original vs `…922` Linux) and that is what drifts."* On
  macOS arm64 the seed is `Major radius actual: 0.9149999999999919`, identical to the original,
  and the run still diverges — while the Linux host, with the `…922` seed, reproduced the
  original's endpoint. The seed is not the mechanism.
- *"the cap-vs-ftol termination mode flips on thread count alone."* Not for the shipped macOS
  binary, which has no OpenMP at all.

Note also that the `J = 1.35036370e-3` / `|dJ| = 2.10437e-2` probe at x0 exercises only the
`SquaredFlux` term: at the seed the coil is 0.887 m (target 1.7), coil-coil 0.096 m (threshold
0.05), coil-surface 0.056 m (threshold 0.015) and curvature is under 60, so all four penalty terms
contribute exactly zero to both J and ∇J. The probe is good evidence for the flux term and no
evidence at all for the penalty configuration. That configuration was instead verified directly
against `simsopt-surrogate@ed120da4e230:examples/single_stage_optimization/STAGE_2/banana_coil_solver.py`:
the objective assembly, the `minimize(..., bounds=, maxcor=300, ftol, gtol)` call and the defaults
(`ftol` 1e-15, `curvature_p_norm` 4, `squared_flux_weight` 1.0) all match, and
`src/simsoptpp/curve{,cwsfourier}.{cpp,h}`, `src/simsopt/geo/curveobjectives.py` and
`src/simsopt/geo/curve.py` are byte-identical between that commit and `bf46e107`.

For reference, the original run was itself a hardware failure — its `results.json` records
`HARDWARE_CONSTRAINTS_OK: false` with coil-coil spacing, max curvature and coil length all in
violation.
